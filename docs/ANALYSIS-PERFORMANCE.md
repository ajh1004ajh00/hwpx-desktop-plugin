# #26 문서 분석 측정과 제한 설계

2026-09-14, Windows x64, Node v24.19.0. `node --expose-gc scripts/benchmark-analysis.mjs` 실행. 각 시나리오 3회, 실제 `analyzeDocument`/`analyzeCurrentTable`와 합성 WASM 형태 어댑터를 사용했다. 실제 WASM 호출·파일 파싱·화면 렌더링·Desktop 응답 시간은 포함하지 않는다. 입력은 합성 문자열뿐이다.

## 제한 구현 전 관찰 결과

시간은 분석 및 JSON 직렬화의 합계, 3회 중앙값(ms)이다. 전후 JSON 바이트와 조회 횟수는 동일하다.

| 입력(한 항목 요청) | 변경 전 | 변경 후 | JSON bytes | 서식 조회 |
|---|---:|---:|---:|---:|
| 본문 5,001자, 같은 서식 | 8.75 | 4.73 | 15,558 | 5,001 |
| 본문 50,000자, 같은 서식 | 52.54 | 25.15 | 150,557 | 50,000 |
| 본문 50,000자, 매 글자 서식 변경 | 176.53 | 73.08 | 8,753,172 | 50,000 |
| 셀 50,000자, 매 글자 서식 변경 | 173.54 | 72.28 | 8,753,174 | 50,000 |
| 한 셀에 1,000자 문단 100개 | 113.42 | 33.96 | 322,328 | 100,000 |
| 10,000문단·1,000페이지에서 100자 한 문단 요청 | 3.32 | 2.89 | 861 | 100 |

마지막 경우 텍스트는 요청한 문단만 읽지만 페이지 layout 조회는 매 요청 1,000회다. 이 fixture에는 제어 객체가 없으므로 복잡한 표 문서의 catalog 비용으로 일반화하지 않는다.

`formatRuns`에서 매 글자의 JSON 비교 문자열과 마지막 전체 객체 복사를 제거했다. 정규화된 서식 필드를 비교하고 완성한 run을 직접 반환한다. 기존 끝부분 접근·병합 구간·페이지 상태 검증 테스트는 통과했다. 응답 크기 자체는 아직 줄지 않았다.

메모리는 분석 전과 직렬화 후 heapUsed 차이이며 peak가 아니다. 매 글자 서식 변경 본문은 약 45.9–47.3MB에서 24.2–26.5MB로 줄었지만, 100문단 셀은 약 7.7–7.8MB에서 33.2–33.3MB로 증가했다. GC 실행 시점에 영향을 받으므로 전체 메모리 개선을 주장하지 않는다. 원자료는 로컬 `test-results/analysis-benchmark.json`과 `analysis-benchmark-after.json`에 있다.

## 제한 구현 전 설계 기준

한 항목으로도 8.75MB가 되므로 항목 수만 줄여서는 해결되지 않는다. 다음 구현은 아래 조건을 함께 충족해야 한다.

1. 문단 내부 textOffset 및 셀 내부 paragraphOffset/textOffset으로 이어 읽는다. 잘림 여부와 다음 위치를 명시하고, 빈 문단·마지막 글자·마지막 서식까지 도달하는 테스트를 만든다.
2. 요청당 텍스트/서식 조회 예산과 직렬화 byte 상한을 별개로 둔다. 실측의 약 175 bytes/run을 기준으로 512자 조각·256KiB 응답을 초기 검증 후보로 삼되 최종값으로 확정하지 않는다. 긴 글꼴명 등 메타데이터로 상한을 넘는 경우까지 다룬다.
3. 여러 항목·셀의 모든 문단을 읽은 후 결과만 자르는 방식은 처리량 제한이 아니다. 예산을 읽기 전에 적용하고 반환 조각만 서식을 조회한다.
4. 이어 읽기도 기존 snapshot의 epoch/changeSeq/SHA/layout 상태에 묶는다. 직접 입력·AI 쓰기·Undo/Redo·문서 교체·레이아웃 변경 뒤 이전 continuation은 거부한다. 상태 키 일부만 같다고 재사용하지 않는다.
5. 현재는 catalog 캐시를 추가하지 않는다. 실제 WASM 경계에서 비용을 측정한 뒤 필요하다면 위 상태 전체를 키로 하는 크기 제한 캐시를 검토한다.
6. 모델에는 #20의 허용 정보와 명시적 분석 범위만 제공한다. 내부 상태 해시나 커서 토큰을 continuation에 노출하지 않는다.

위 내용은 제한 구현 전 기록이다. 후속 구현과 현재 남은 검증은 아래에 구분한다.

## 2026-09-14 후속 구현: 제한 및 이어 읽기

- 공통 예산: 요청당 최대 512 native 텍스트 위치 단위 및 서식 조회, 50 문단 조각. 항목 수 limit 1–50도 유지한다. 본문/현재 표/문서 내 셀 모두 읽기 전에 같은 예산을 차감한다. 빈 문단도 서식 조회 1회를 소비한다.
- JSON 응답 상한 256 KiB. 후속 항목을 추가하면 예산을 넘는 경우 해당 항목 앞의 위치를 반환한다. 단일 항목의 비정상적으로 큰 스타일/글꼴 등 메타데이터는 ANALYSIS_ITEM_TOO_LARGE로 명시적으로 거부한다. 메타데이터를 몰래 잘라 성공으로 반환하지 않는다. 이 경우 해당 항목의 세부 분석은 현재 지원 한계다.
- next = {offset, paragraphOffset, textOffset}, 없으면 null. 같은 snapshot_id와 limit로 next 필드를 그대로 전달한다. 부분 항목에서는 nextOffset이 같은 값으로 반복될 수 있어 nextOffset만 쓰면 안 된다. 각 문단 조각에는 전체 length, 시작 textOffset, truncated, 원래 문단 기준 formatRuns 위치를 제공한다.
- next에는 상태 해시나 문서 내용이 없다. 매 요청에 기존 private snapshot의 epoch/changeSeq/SHA/layout 전체를 읽기 전후 대조한다. 상태가 바뀌면 새 snapshot으로 처음부터 다시 분석한다. 문서 캐시는 추가하지 않았다.
- 512/256 KiB는 합성 측정에 근거한 현재 구현 기본값이다. 실제 WASM/host 검증으로 최종 출시값을 확정해야 한다.

검증: 전체 Node 테스트 34개 통과, Vite 빌드 성공, git diff --check 통과. 추가 사례는 긴 본문/셀 5,001자 끝 접근, 여러 문단/빈 문단, 총 조회 예산, byte 경계에서 다음 항목 재개, oversized 메타데이터 거부, 상태 필드 각각 변경 및 읽는 도중 변경 거부, WebMCP의 동일 snapshot 전달과 상태 비노출이다. 실제 Undo/Redo/문서 교체의 UI 조작을 대신 수행한 결과가 아니라 상태 계약을 합성으로 검증한 결과다.

# 실제 WASM 전체 읽기 후속 측정 (2026-09-14)

`node scripts/benchmark-native-analysis.mjs`는 37페이지/33문단/63,991자의 합성 문서를 실제 rhwp 0.8.6 WASM으로 끝까지 읽고 `test-results/native-analysis.json`에 기록한다. 125개 응답과 동일 텍스트를 유지하면서 문서 카탈로그 재사용으로 레이아웃 조회가 4,625회에서 37회로 줄었다. 단일 실행 시간은 2,439ms→1,786ms였다. 정적 상태 어댑터 측정이므로 host의 상태 해시 계산·UI 지연이나 peak 메모리를 포함한다고 주장하지 않는다. 모델 객체·epoch/changeSeq/SHA/layoutPageCount 변경 및 분석 오류에 대한 캐시 폐기를 테스트했다.
# 2026-09-14 메모리 계측 보완

`benchmark-native-analysis.mjs`는 응답마다 RSS/heap을 샘플링하고 Node `process.resourceUsage().maxRSS`도 기록한다. 이번 실행(Windows x64, Node 24.19.0)의 프로세스 수명 최대 RSS는 230,891,520바이트, 캐시 사용 순회의 샘플 최대 RSS는 97,841,152바이트, WASM 할당은 5,963,776바이트였다. 응답별 샘플링은 응답 사이의 순간 peak를 놓칠 수 있다. 수명 최대값에는 초기화·합성 문서 생성·두 가지 순회가 모두 포함되고, 두 방식을 같은 프로세스에서 순차 실행하므로 메모리 절감 비교 또는 브라우저 실제 peak로 해석하지 않는다.
